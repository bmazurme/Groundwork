# docs: третий раунд анализа — 5 новых предложений (Issue 011–015)

## Что сделано
Статический анализ `apps/backend` и `apps/frontend` (документы, процессор индексации, поиск, эмбеддинги, хранилище, клиент API). Код приложения **не менялся**; приложение, тесты и Docker не запускались (в снимке нет `.git`, зависимостей и `init.md`).

1. **Открытые Issue.** В снимке нет `ISSUES.md` и данных трекера, поэтому открытых Issue для работы нет. Задачи из предыдущих раундов (`IMPROVEMENTS.md`, Issue 001–010) не реализовывались: это задание про анализ и предложения.
2. **Новые предложения** (5, не больше) оформлены как тексты Issue в `docs/issues/011…015-*.md`, индекс обновлён в `docs/issues/README.md`. Дубликатов нет: я сверил темы с 001–010 и `IMPROVEMENTS.md`.
3. **Почему не созданы в трекере.** Из этого запуска можно опубликовать только файлы одним PR; `.lab/issue.json` открывает ровно один Issue и только без других изменений файлов. Пять Issue так не создать, поэтому тексты лежат в `docs/issues/`; владельцу достаточно завести Issue из них (заголовок и тело берутся как есть).

## Предлагаемые решения

| Issue | Проблема (где найдено) | Решение | Зависимости |
|---|---|---|---|
| 011 | Эмбеддинг и `INSERT` по одному чанку (`documents.processor.ts`); воркер и ONNX в одном процессе с API, поиск ждёт индексацию; конкурентность не задана | Необязательный `embedBatch` в `EmbeddingsProvider`, пакетная вставка, `APP_ROLE=api\|worker\|all`, `INDEX_CONCURRENCY`, замер этапов | Согласуется с транзакцией из `IMPROVEMENTS.md` п. 3 |
| 012 | Нет request id, структурных логов и метрик | JSON-логи, `X-Request-Id`, `/api/metrics` (Prometheus) по флагу, без записи текста запросов | Новая: `prom-client` (нужен для формата; перед добавлением `npm audit`) |
| 013 | `upload` сначала удаляет старый объект S3 и лишь потом делает `UPDATE`; сбой оставляет строку с несуществующим ключом; `remove` проглатывает ошибки S3, сироты копятся | Порядок: новый объект → БД → удаление старого; `storage:reconcile` (dry-run по умолчанию) | Нет |
| 014 | Нигде не записано, какой моделью посчитан вектор; смена провайдера тихо портит поиск | `modelId`/`dimensions` у провайдера, `documents.embedding_model`, проверка при старте, фильтр векторной ветки, `reindex --stale` | Миграции (`IMPROVEMENTS.md` п. 4) |
| 015 | Оригинал в S3 недоступен через API; пользователь видит только чанки | `GET /documents/:id/file` (стрим, RFC 5987, защитные заголовки для HTML), кнопки на фронтенде | Issue 002, 007 |

## Рекомендуемый порядок
013 (небольшой риск потери файла, дёшево) → 011 → 012 → 014 (после миграций) → 015. Вместе с прежними списками: миграции → eval → остальное.

## Совместимость и риски
- Публичный контракт `/api` не меняется. Предложения добавляют только необязательные поля и новый маршрут (015, 014: `staleEmbeddings` в health); фронтенд обновляется в том же коммите при реализации.
- Размерность эмбеддингов и схема `document_chunks` не затрагиваются; Issue 014 как раз добавляет защиту этой связки. Смена модели и пересчёт данных остаются решением владельца (dry-run по умолчанию).
- Dockerfile бэкенда остаётся на `node:22-slim`.

## Допущения и ограничения
- Анализ статический, замеров нет: утверждения о задержке поиска во время индексации (011) выведены из того, что воркер и API работают в одном процессе, и требуют замера (он есть в критериях приёмки).
- Для 014 допущено, что существующие документы проиндексированы моделью по умолчанию; владельцу нужно подтвердить.
- Изменения `.github/workflows/` в PR не входят.
- Проверок lint/build/test для документации нет.
