## Предложения и обоснование

### 026 — Гонки при параллельной загрузке и индексации
- **Найдено:** нет `UNIQUE (name)` и `UNIQUE (document_id, chunk_index)`; `upload()` — `SELECT` + `INSERT/UPDATE`, поэтому две одновременные загрузки дают дубликат документа или одинаковую `version` и общий S3-ключ; задания на разные версии могут перемешать чанки; удаление во время индексации даёт бессмысленные ретраи; старое задание выставляет `indexed` для уже новой версии.
- **Решение:** `INSERT ... ON CONFLICT`, условный `UPDATE ... WHERE version = $2` в конце индексации, `jobId` с версией, advisory lock, миграция с уникальными индексами, которая при дубликатах падает, а не удаляет данные.

### 027 — Очередь BullMQ
- **Найдено:** `forRoot` без `defaultJobOptions`: по умолчанию завершённые и упавшие задания хранятся в Redis бессрочно; `lockDuration` и concurrency не заданы, при блокировке event loop эмбеддингами задание может стать stalled и выполниться дважды; у Redis нет `noeviction`/персистентности в compose.
- **Решение:** общие `DEFAULT_JOB_OPTIONS`, параметры из env, `appendonly yes` и `noeviction` для Redis, единая фабрика постановки в очередь.

### 028 — Загрузка нескольких файлов
- **Найдено:** `handleFiles` берёт только первый файл, остальные игнорируются молча; при перетаскивании тип не проверяется; подпись форматов не упоминает `.txt`; нет клиентского предела размера.
- **Решение:** `multiple`, функция `validateUpload`, последовательная очередь с отдельным статусом на файл. Серверный контракт (один файл на запрос) не меняется.

### 029 — Доступность
- **Найдено:** в `src` три упоминания `aria`/`role`; результат поиска и смена статуса документа не объявляются скринридеру; dropzone без `aria-disabled`; контраст не проверялся.
- **Решение:** живые области с объявлением итога (важно до появления стриминга), `aria-label` для иконок, `cypress-axe` в CI (единственная новая dev-зависимость, с проверкой `npm audit`).

### 030 — Резервное копирование
- **Найдено:** состояние в двух хранилищах (Postgres и S3), в README нет процедуры бэкапа и восстановления; `docker compose down -v` стирает всё; рассинхрон после частичного восстановления превращается в `failed` при повторной индексации.
- **Решение:** скрипты `backup.sh`/`restore.sh` с манифестом (версия схемы, модель, размерность), проверка целостности S3↔БД, плановая проверка восстановления в CI.

- Публичный контракт `/api` в этом PR не меняется; при реализации ни одно из пяти предложений его не ломает (028 оставляет один файл на запрос).
