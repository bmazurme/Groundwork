# Issue 026: Гонки при параллельной загрузке и индексации одного документа

**Метки:** bug-candidate, backend, data-integrity

## Проблема
Найдено чтением кода (`documents.service.ts`, `documents.processor.ts`, `database/schema.ts`); на запущенном стеке не воспроизводилось.
- **Нет уникальности имени.** `upload()` делает `SELECT ... WHERE name = $1`, затем `INSERT` или `UPDATE`. В таблице `documents` нет `UNIQUE (name)`. Два одновременных запроса с одним новым именем оба не находят строку и создают два документа, а дубликат «версии» уже не схлопнуть. Для существующего документа два параллельных `UPDATE` читают одну и ту же `version` и оба пишут `version + 1`; ключи S3 при этом совпадают (`documents/{id}-v{n}-{name}`), и один объект перезаписывает другой.
- **Конкурирующие задания на один документ.** Каждая загрузка ставит своё задание `process`. Воркер не знает, актуально ли оно. Если за короткое время пришли две версии, два задания выполняются параллельно (concurrency воркера по умолчанию 1, но при нескольких репликах или росте concurrency из Issue 011 это не так). Их `DELETE FROM document_chunks` и `INSERT` перемешиваются, и в итоге могут остаться чанки от двух версий (дубликаты `chunk_index`). Уникального индекса `(document_id, chunk_index)` нет, база этого не запретит.
- **Удаление во время индексации.** Если документ удалён между `SELECT` и вставкой чанков, `INSERT` падает по внешнему ключу, и задание уходит в ретраи (`attempts` из `IMPROVEMENTS.md`, п. 3), хотя повторять нечего. `UPDATE ... status = 'failed'` затрагивает 0 строк без ошибки.
- **Устаревший статус.** Старое задание, завершившись после новой загрузки, выставляет `indexed` для документа, у которого уже `pending` и новый `s3_key`.

## Предложение
1. Миграция (после `IMPROVEMENTS.md`, п. 4): `UNIQUE (name)` на `documents` и `UNIQUE (document_id, chunk_index)` на `document_chunks`. Перед созданием индекса проверить существующие дубликаты запросом и описать ручную очистку в README (автоматическое удаление данных необратимо, поэтому миграция при дубликатах должна падать с понятным сообщением, а не удалять).
2. `upload()`: один оператор `INSERT ... ON CONFLICT (name) DO UPDATE SET version = documents.version + 1, ... RETURNING id, version, (xmax = 0) AS inserted` вместо `SELECT` + `INSERT/UPDATE`. Старый `s3_key` нужно получить до обновления (`SELECT ... FOR UPDATE` в той же транзакции), чтобы корректно удалить предыдущий объект.
3. Воркер: в начале обработки читать `version` и `s3_key`; индексацию вести в одной транзакции (совпадает с п. 3 `IMPROVEMENTS.md`); в конце `UPDATE ... WHERE id = $1 AND version = $2`. Если затронуто 0 строк, документ удалён или заменён новой версией: откатить транзакцию и завершить задание без ошибки (`return`), а не бросать исключение.
4. Передавать в `queue.add` `jobId = ${documentId}:v${version}`: повторный клик или ретрай запроса не создаёт дубль задания.
5. Для сериализации работы с одним документом использовать `pg_advisory_xact_lock(hashtext(documentId))` в транзакции индексации; новых зависимостей не требуется.

## Критерии приёмки
- Интеграционный тест (Issue 020): `Promise.all` из 5 загрузок файла с одним именем даёт один документ, `version = 5` (или ровно число успешных ответов), одну строку в `documents`.
- Тест: два задания на разные версии подряд оставляют чанки только последней версии, без дубликатов `chunk_index`, статус `indexed` соответствует актуальной версии.
- Тест: удаление документа в момент индексации не приводит к ретраям и к статусу `failed`; задание завершается успешно как no-op.
- Контракт `/api` не меняется.
