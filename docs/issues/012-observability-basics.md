# Issue 012: Базовая наблюдаемость: структурные логи, request id, метрики Prometheus

**Метки:** ops, observability

## Проблема
В бэкенде используется только стандартный `Logger` Nest в текстовом виде. Нет идентификатора запроса, нет метрик (количество документов по статусам, глубина очереди, задержка поиска, ошибки индексации). Диагностировать «поиск стал медленным» или «очередь стоит» можно только вручную. Langfuse из задания продукта покрывает трассировку LLM-пайплайна, но не эксплуатационные метрики сервиса, и по умолчанию выключен.

## Предложение
- Структурные JSON-логи в production (`LOG_FORMAT=json|text`, по умолчанию `text`) с полем `requestId` (заголовок `X-Request-Id`, иначе генерируется; возвращается в ответе и попадает в логи процессора через данные задачи).
- Эндпоинт `GET /api/metrics` (формат Prometheus) через `prom-client`: `http_request_duration_seconds` (метка маршрута, без `q`), `search_duration_seconds`, `documents_total{status}`, `queue_jobs{state}`, `indexing_duration_seconds`, `indexing_failures_total`. Включается `METRICS_ENABLED=true`, по умолчанию выключено; при API-ключе из Issue 002 — защищать им.
- Не писать текст запросов пользователей и содержимое документов в логи на уровне info.

## Зависимости
Одна новая: `prom-client` (стандартный клиент Prometheus, нужен для формата экспозиции). Перед добавлением — `npm audit`. Для JSON-логов своя тонкая реализация `LoggerService`, без `pino`.

## Критерии приёмки
- Юнит-тест форматтера логов и интерсептора (метка маршрута — шаблон `/documents/:id/chunks`, а не реальный URL, чтобы не раздувать кардинальность).
- `curl /api/metrics` показывает счётчики после загрузки документа и поиска.
- При `METRICS_ENABLED` не задан эндпоинт отвечает 404.

## Риски
Кардинальность меток; утечка содержимого запросов в логи — проверить тестом.
