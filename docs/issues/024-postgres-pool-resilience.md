# Issue 024: Пул Postgres без обработчика ошибок и таймаутов: обрыв соединения может уронить процесс, а медленный запрос повесить API

**Метки:** reliability, backend

## Проблема
- `database.module.ts` создаёт `new Pool({ connectionString })` без обработчика `pool.on('error', ...)`. В `pg` ошибка на *простаивающем* клиенте (рестарт Postgres, обрыв сети, `idle_in_transaction_session_timeout`) эмитится как событие `error` пула; без слушателя это необработанное событие `EventEmitter`, и процесс Node завершается. Для API с одной точкой отказа это значит падение всего бэкенда при кратком перезапуске БД, хотя `connectWithRetry` рассчитан именно на такие сбои при *старте*.
- Нет `connectionTimeoutMillis`, `statement_timeout`, `max`, `idleTimeoutMillis`. Если все клиенты пула заняты (по умолчанию 10) долгими запросами индексации, поиск и `/health` встают в очередь без ограничения по времени. Это связано с тем, что воркер BullMQ (`documents.processor.ts`) и HTTP-слой делят один пул.
- `/api/health` выполняет `SELECT 1` через тот же пул, поэтому при исчерпании пула health-check зависает вместо того, чтобы вернуть `degraded`.
- Для Redis (`queue.module.ts`) параметры подключения тоже минимальные: нет `maxRetriesPerRequest: null`-проверки под воркер BullMQ и обработчика ошибок соединения (в логах будет шум `ioredis` без контекста).

## Предложение
- В фабрике пула: `pool.on('error', (err) => logger.error(...))`, без выхода из процесса; последующие запросы получат новое соединение.
- Параметры из env с безопасными значениями по умолчанию: `PG_POOL_MAX` (по умолчанию 10, как сейчас), `PG_CONNECTION_TIMEOUT_MS` (5000), `PG_STATEMENT_TIMEOUT_MS` (30000; для миграций и тяжёлой индексации можно задавать отдельно), `PG_IDLE_TIMEOUT_MS` (30000).
- `/health`: запрос с собственным коротким таймаутом (`Promise.race` c 2 с или `SET LOCAL statement_timeout`), чтобы при проблемах отвечать `degraded`, а не зависать. Добавить в ответ счётчики `pool.totalCount`, `idleCount`, `waitingCount` — они дешёвые и дают базовую диагностику (согласуется с Issue 012).
- Рассмотреть отдельный небольшой пул для воркера индексации (`PG_WORKER_POOL_MAX`), чтобы индексация не вытесняла поиск. Если оценка покажет, что это избыточно, зафиксировать решение в README.
- Логирование ошибок соединения BullMQ/Redis через `connection.on('error')`.

## Критерии приёмки
- Юнит-тест фабрики: ошибка, эмитированная на пуле, не бросает исключение и пишется в лог; параметры читаются из env с указанными значениями по умолчанию.
- Ручная проверка (записать в PR): при работающем приложении `docker compose restart postgres` — процесс бэкенда не завершается, `/api/health` показывает `degraded`, затем возвращается в `ok`, поиск снова работает без перезапуска бэкенда.
- Тест: при занятых всех соединениях `/health` отвечает за ≤ 2 с с `database: 'down'`.

## Контракт
`/api/health` получает необязательное поле с метриками пула (добавление, существующие поля сохраняются; фронтенд читает только `status`/`database`). Новые env-переменные добавляются в `.env.example` и README.
