# Issue 018: Парсинг недоверенных файлов в основном процессе: нет таймаута и лимитов, `pdf-parse` 1.1.1 не поддерживается

**Метки:** security, reliability, dependencies

## Проблема
Найдено чтением `documents.processor.ts`, `parsing/parse-document.ts`, `package.json`; на стеке не проверялось.
- `parseDocument` вызывается внутри процесса API/воркера (один процесс, см. Issue 011) без таймаута и без ограничения памяти. Специально сделанный PDF/DOCX (глубоко вложенные объекты, «zip-бомба» в DOCX — это ZIP, который `mammoth` распаковывает целиком) может надолго занять event loop или исчерпать память и уронить **весь** бэкенд, включая поиск. `IMPROVEMENTS.md` п. 3 предлагает лимит размера загрузки, но он не защищает от малого по размеру файла с большим распакованным содержимым.
- `pdf-parse@^1.1.1` — последняя версия 2018 года, пакет не развивается; внутри старый `pdfjs`. Это риск как безопасности (известные уязвимости старых версий pdf.js), так и качества (Issue 006). Нужно проверить `npm audit` и актуальность альтернатив (`pdfjs-dist` напрямую или `unpdf`), не выбирая вслепую.
- Размер результата не ограничен: огромный извлечённый текст даст десятки тысяч чанков и столько же вызовов эмбеддера (дорого и медленно), а таблица `document_chunks` и индекс HNSW разрастутся.
- Ошибка парсинга сохраняется в `failure_reason` как есть, включая внутренние пути и стек-фрагменты библиотек.

## Предложение
1. Выполнять парсинг в отдельном контексте с таймаутом: `worker_threads` (с `resourceLimits.maxOldGenerationSizeMb`) или дочерний процесс; по таймауту (`PARSE_TIMEOUT_MS`, по умолчанию 60 с) задача завершается ошибкой «Parsing timed out». Новых зависимостей не нужно.
2. Лимиты: `MAX_EXTRACTED_CHARS` (например, 5 млн символов) и `MAX_CHUNKS_PER_DOCUMENT`; при превышении документ `failed` с понятной причиной, а не тихо усечённый индекс.
3. Для DOCX перед `mammoth` проверить суммарный распакованный размер записей ZIP по центральному каталогу (чтение каталога без распаковки) и отклонить файл выше порога.
4. Оценить замену `pdf-parse`: прогнать набор тестовых PDF (текстовый, таблицы, кириллица, скан) на кандидатах, сравнить результат и `npm audit`, затем решить. Замену делать отдельным коммитом и только по результатам сравнения.
5. В `failure_reason` писать нормализованное сообщение (`ParseError` с кодом), подробности — в логе.

## Критерии приёмки
- Юнит-тест: «зависающий» парсер (подмена) прерывается по таймауту, процесс-родитель жив и продолжает отвечать.
- Тест: DOCX с распакованным размером выше лимита отклоняется до вызова `mammoth`.
- Документ с превышением `MAX_CHUNKS_PER_DOCUMENT` получает `failed` и понятную причину.
- Если зависимость заменяется: в PR указана причина и результат `npm audit` до/после.

## Риски
Потоки/процессы усложняют отладку и передачу `Buffer` (копирование). На малых файлах накладные расходы незаметны, на больших нужен замер. Изменение парсера меняет текст чанков и требует ручной переиндексации (Issue 016).
