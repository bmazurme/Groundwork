# Issue 013: Согласованность S3 и Postgres: «осиротевшие» объекты и невидимая потеря файла

**Метки:** reliability, data

## Проблема
Найдено чтением `documents.service.ts`:
- `upload`: сначала `storage.upload`, затем `INSERT/UPDATE`. Если запись в БД падает, объект в бакете остаётся без строки в `documents`.
- Повторная загрузка с тем же именем **сначала удаляет старый объект** (`storage.delete(previous.s3_key)`), и только потом делает `UPDATE`. Если `UPDATE` упадёт, строка продолжит указывать на удалённый ключ: документ останется `indexed`, но переиндексация и «открыть оригинал» будут ломаться, а ошибка не будет видна.
- `remove`: строка удаляется, затем объект удаляется «по возможности» (ошибка проглатывается). Любой сбой S3 оставляет мусор навсегда; видимости для владельца нет.
- Нет способа проверить, что каждый `s3_key` из БД реально существует, и наоборот.

## Предложение
- Порядок в `upload`: загрузить новый объект → `UPDATE` в БД → только после успеха удалять старый объект (ошибка удаления логируется, не блокирует).
- Скрипт/эндпоинт сверки `npm run storage:reconcile` (dry-run по умолчанию, `--apply` для удаления): список ключей бакета с префиксом `documents/` против `documents.s3_key`; осиротевшие старше `ORPHAN_GRACE_HOURS` (по умолчанию 24, чтобы не задеть загрузку «в полёте») удаляются; строки с отсутствующим объектом помечаются `failed` с понятным `failure_reason`.
- Опционально: правило жизненного цикла бакета для незавершённых multipart-загрузок (в README).

## Критерии приёмки
- Юнит-тесты `upload` с фейковым хранилищем и БД, где `UPDATE` падает: старый объект цел, новый удалён или учтён как осиротевший.
- Тест сверки на фейковых списках ключей: dry-run ничего не удаляет, `--apply` удаляет только осиротевшие старше грейса.
- Ручной сценарий на MinIO: удалить объект в консоли → сверка помечает документ `failed`.

## Риски
Удаление данных необратимо, поэтому `--apply` только явный; по умолчанию dry-run и логирование списка.
