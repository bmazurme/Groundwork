# Issue 025: Кириллические имена файлов при загрузке (кодировка multer) и обработка `.txt` как Markdown

**Метки:** bug-candidate, backend, i18n

## Проблема
- Продукт заявлен как RU+EN, а `documents.controller.ts` использует `FileInterceptor` с `memoryStorage()`, и `documents.service.ts` берёт `file.originalname` как есть: для `name` документа, для поиска существующей версии (`WHERE name = $1`) и для S3-ключа. `multer`/`busboy` по умолчанию разбирают заголовок `filename` в `multipart` как `latin1`, поэтому UTF-8 имя вроде «Регламент.pdf» может сохраниться как «Ð ÐµÐ³Ð»Ð°Ð¼ÐµÐ½Ñ‚.pdf». **Это гипотеза по поведению библиотеки, не подтверждённая запуском** (в снимке нет зависимостей): первым шагом нужно воспроизвести на текущих версиях `multer`/`busboy`.
- Если гипотеза верна, то: в таблице документов и в `sources[].documentName` показываются «кракозябры»; повторная загрузка того же файла из разных клиентов может создавать дубликаты (разные байты имени); ключ S3 содержит мусор; Issue 015 (скачивание с именем на кириллице) унаследует дефект.
- Нормализация Unicode не выполняется: «й» в NFC и в NFD (имена из macOS) это разные строки, и повторная загрузка с Mac создаст второй документ вместо новой версии.
- `.txt` отображается в формат `markdown` (`formatFromFilename`) и обрабатывается как Markdown: строки `---`, `#` и «```» в обычном тексте будут восприняты как frontmatter/заголовки/код. Для UI формат показывается как `markdown`, хотя пользователь загрузил `.txt`.

## Предложение
1. **Воспроизвести:** тест `supertest` на `POST /api/documents` с файлом `Регламент.md` и проверкой `name` в ответе (в интеграционном наборе Issue 020 или изолированный unit-тест на контроллер).
2. Если подтверждено: функция `normalizeFilename(raw: string): string` в `documents/` — если строка не содержит символов вне диапазона latin1 и после `Buffer.from(raw, 'latin1').toString('utf8')` не появляется `U+FFFD`, использовать перекодированное значение; затем `.normalize('NFC')`, удаление управляющих символов и путевых разделителей, обрезка до 200 символов. Либо передать `defParamCharset: 'utf8'` в опции multer, если версия её поддерживает (предпочтительнее: проверить и использовать без самодельной эвристики).
3. Применять нормализацию до `SELECT ... WHERE name = $1` и до построения S3-ключа. Существующие записи с испорченными именами не перезаписывать автоматически (необратимо); описать в README команду/запрос для ручной проверки.
4. `.txt`: добавить значение формата `text` (или обрабатывать `.txt` в `chunkText` с `markdown: false`). Это добавление значения в `DocumentFormat` затрагивает контракт, поэтому вносится вместе с фронтендом (`api/types.ts`, фильтр форматов в `DocumentsTable`) в одном коммите. Если владелец предпочитает не менять контракт, то минимально: `parse` помечает `.txt` как `markdown: false` внутри процессора по расширению имени.

## Критерии приёмки
- Юнит-тесты `normalizeFilename`: ASCII без изменений; mojibake-вход «Ð ÐµÐ³...» → «Регламент»; уже корректная кириллица не портится (идемпотентность); NFD → NFC; `../x.md` → безопасное имя.
- Интеграционный сценарий: загрузка «Регламент.md» дважды → один документ, `version = 2`, `name` корректный в ответе, в списке и в `sources`.
- Тест чанкера/процессора: текст `.txt` со строками `---` и `#` не интерпретируется как frontmatter/заголовок.

## Контракт
Если выбирается новый формат `text`, изменяется `DocumentFormat` (описать в PR, обновить фронтенд в том же коммите). Иначе контракт не меняется.
