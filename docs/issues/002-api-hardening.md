# Issue 002: Защита API — валидация входа, лимиты запросов, заголовки, опциональная авторизация

**Метки:** security, backend

## Проблема
- `main.ts` не подключает `ValidationPipe`, `helmet` и rate limiting. Эндпоинты `/api/search`, `/api/documents` открыты без какой-либо авторизации.
- `GET /api/search?q=` принимает строку любой длины. Каждый запрос запускает эмбеддинг на CPU и два SQL-запроса, поэтому дёшево устроить перегрузку (DoS).
- Параметр `q` может прийти массивом (`?q=a&q=b`), тогда `query.trim()` падает с 500.
- `originalname` попадает в S3-ключ (`documents/${id}-v${n}-${originalname}`) без нормализации. Сам ключ безопасен для S3, но имена со спецсимволами и очень длинные имена дают некрасивые ключи и ошибки.
- CORS настроен на один origin, но без явных методов и заголовков.

## Предложение
- Глобальный `ValidationPipe` (`whitelist`, `transform`) и DTO для `q` (строка, `MaxLength(500)`), `ParseUUIDPipe` для `:id` (пересекается с п. 3 в `IMPROVEMENTS.md`, делать вместе).
- `@nestjs/throttler` с лимитом на `/search` и `/documents` (значения через env, по умолчанию мягкие).
- `helmet`.
- Опциональный API-ключ: `API_KEY` в env. Если он не задан, поведение не меняется. Если задан, нужен заголовок `Authorization: Bearer`, а фронтенд получает ключ через `VITE_*` или прокси.
- Санитизация имени файла для S3-ключа, ограничение длины.

## Зависимости (обоснование)
`class-validator` и `class-transformer` нужны для DTO. `@nestjs/throttler` нужен для лимитов. `helmet` ставит заголовки безопасности. Перед добавлением выполнить `npm audit`.

## Критерии приёмки
- e2e: `q` длиннее лимита → 400. `q` массивом → 400, не 500.
- e2e: при заданном `API_KEY` запрос без заголовка → 401.
- Превышение лимита запросов → 429.
- Без новых env поведение API прежнее.

## Контракт
Новые коды ошибок (400/401/429). Фронтенд должен показывать их читаемо (см. Issue 004).
