# Issue 009: Поиск нельзя ограничить документами, форматом или набором («коллекцией»)

**Метки:** search, api, ux

## Проблема
`GET /api/search?q=...` всегда ищет по всем документам. Когда в библиотеке накапливаются документы разных тем (политики, инструкции, договоры), ответы из чужих областей вытесняют нужные, а пользователь, который точно знает, в каком документе искать, не может это сказать. Фронтенд при этом уже умеет фильтровать список документов по формату и статусу, но фильтры на поиск не влияют.

## Предложение
Этап 1 (без схемы):
- Необязательные параметры `/api/search`: `documentId` (повторяемый), `format`. В SQL обеих веток (`fullText`, `vector`) добавить `AND dc.document_id = ANY($n::uuid[])` и `AND d.format = ANY($n::text[])`. Параметры валидировать (UUID, enum форматов; связано с Issue 002).
- Важно: для векторной ветки фильтр сочетается с HNSW через post-filtering, и при узком фильтре индекс может вернуть меньше `LIMIT` строк. Включить `SET LOCAL hnsw.iterative_scan = relaxed_order` (pgvector ≥ 0.8; проверить версию образа `pgvector/pgvector:pg16`) либо увеличивать `CANDIDATES_PER_METHOD` при наличии фильтра. Проверить измерением, не предполагать.
- Фронтенд: в `SearchPanel` выбор «Искать в: все документы / выбранные» (мультиселект Gravity UI из `useQuery(documents)`).

Этап 2 (отдельным решением владельца, со схемой): таблица `collections` и связь с документами, поиск по `collectionId`.

## Критерии приёмки
- Тесты: запрос с `documentId` возвращает только чанки этого документа; несуществующий `documentId` → пустая выдача, не 500; некорректный UUID → 400.
- Без параметров поведение и результаты прежние (обратная совместимость).
- Проверка на реальных данных, что при фильтре по одному документу выдача не пустеет, если в нём есть релевантные чанки (проверка iterative scan).

## Риски
На малых объёмах дополнительные индексы не нужны, но при росте корпуса стоит замерить планы запросов с фильтрами. Этап 2 требует миграции (`IMPROVEMENTS.md` п. 4).
