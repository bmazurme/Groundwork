# Issue 031: Типизированная валидация конфигурации (env) при старте

**Метки:** backend, reliability, dx

## Проблема
Переменные окружения читаются россыпью через `process.env.X ?? default` в восьми местах (`main.ts`, `database.module.ts`, `queue.module.ts`, `storage.service.ts`, `embeddings.module.ts`, оба провайдера эмбеддингов). Последствия:
- Опечатка не замечается: `EMBEDDINGS_PROVIDER=ollma` молча выбирает ONNX (в `embeddings.module.ts` проверяется только равенство `'ollama'`).
- `REDIS_PORT=abc` превращается в `NaN` и проявляется поздно, ошибкой подключения к Redis.
- Отсутствующий `DATABASE_URL` даёт `new Pool({ connectionString: undefined })`, то есть тихое подключение к localhost по умолчанию `pg`.
- Новые провайдеры из плана (реранкер, LLM, Langfuse) добавят ещё десяток переменных; без единой точки их список и значения по умолчанию разойдутся с `.env.example` и README.

## Предложение
1. Модуль `config/` с одной функцией `loadConfig(env: NodeJS.ProcessEnv): AppConfig`, возвращающей типизированный объект (`port`, `database.url`, `redis.{host,port}`, `s3.*`, `embeddings.{provider,ollama.*}`). Провайдеры получают его через DI (токен `APP_CONFIG`), а не читают `process.env`.
2. Валидация на старте: значения из закрытых множеств (`onnx|ollama`), числа, URL. При ошибке приложение завершается с перечнем *всех* проблемных переменных, а не первой. Вариант без зависимостей — ручной парсер (~80 строк); вариант с `zod` — короче, но это новая зависимость (по правилам проекта нужно обоснование и `npm audit`). Рекомендация: начать без зависимости.
3. В production-режиме (`NODE_ENV=production`) отсутствие `DATABASE_URL`, `S3_BUCKET` — ошибка, в dev остаются значения по умолчанию.
4. Тест, который сверяет ключи `AppConfig` с `.env.example` (каждая переменная описана), чтобы документация не расходилась.

## Критерии приёмки
- Юнит-тесты `loadConfig`: корректные значения, неверный провайдер, нечисловой порт, несколько ошибок сразу.
- Запуск с `EMBEDDINGS_PROVIDER=ollma` завершается кодом ≠ 0 и сообщением со списком допустимых значений.
- Прямых обращений к `process.env` вне `config/` нет (проверка в lint или тестом-grep).
- Поведение с корректным окружением и контракт `/api` не меняются.
