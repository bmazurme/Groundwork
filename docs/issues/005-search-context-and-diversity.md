# Issue 005: Контекст соседних чанков и разнообразие выдачи при поиске

**Метки:** search-quality, backend, frontend

## Проблема
- Выдача — топ-5 отдельных чанков (`TOP_RESULTS = 5`). Один длинный документ может занять все 5 мест почти одинаковыми кусками (между соседними чанками есть перекрытие 150 символов), вытеснив другие документы.
- Чанк сам по себе часто обрывается на полуслове (разбиение по размеру), и вопрос, ответ на который лежит на стыке чанков, не получает полного контекста. Для будущего LLM-синтеза (`IMPROVEMENTS.md`, п. 5) это критично: модель увидит лишь куски.
- `CANDIDATES_PER_METHOD = 20`, `TOP_RESULTS = 5` и `SEMANTIC_ONLY_MAX_DISTANCE` зашиты в код.

## Предложение
- После RRF применить ограничение на число чанков одного документа (`SEARCH_MAX_PER_DOCUMENT`, по умолчанию 2) или MMR с малым весом разнообразия. Это чистая функция, легко покрывается юнит-тестами. Вынести `reciprocalRankFusion` в отдельный файл вместе с ней.
- Расширение контекста: для каждого попавшего чанка добавлять соседние (`chunk_index ± 1`) в необязательное поле ответа `context` (предыдущий и следующий текст). Старые поля `excerpt` и остальные не менять. Один дополнительный SQL-запрос по `(document_id, chunk_index)`.
- Вынести пороги в env (`SEARCH_TOP_K`, `SEARCH_CANDIDATES`, `SEMANTIC_MAX_DISTANCE`) с текущими значениями по умолчанию.
- Фронтенд: раскрывающийся блок «показать контекст» в `SearchPanel`.

## Критерии приёмки
- Юнит-тесты: ограничение на документ сохраняет порядок по score, не теряет единственный документ, при лимите 1 даёт не более одного чанка на документ.
- Поведение по умолчанию (без новых env) отличается от текущего только лимитом на документ. Если владелец хочет полностью прежнее поведение, значение по умолчанию задаётся равным `TOP_K`.
- Замер на eval-наборе до и после.

## Контракт
Только добавление необязательного поля `context` в элементы `sources`, обратно совместимо.
