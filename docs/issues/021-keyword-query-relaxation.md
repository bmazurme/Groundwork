# Issue 021: Ключевая ветка поиска требует совпадения всех слов вопроса (AND) и почти не работает для вопросов на естественном языке

**Метки:** search, backend, quality

## Проблема
- В `search.service.ts` ключевая ветка использует `websearch_to_tsquery('english', $1)`. Эта функция соединяет все термы запроса через `&`. Для запроса-ключа («e2e», «pgvector») это хорошо, но продукт отвечает на **вопросы**: «как сбросить пароль администратора?». Чанк попадёт в ключевую ветку только если в нём есть *все* значимые слова вопроса. На практике для вопросов из 4+ слов ветка возвращает 0 строк, и гибридный поиск молча превращается в чисто векторный (с порогом `SEMANTIC_ONLY_MAX_DISTANCE`).
- Это отдельная проблема от `IMPROVEMENTS.md` п. 1 (словарь `russian`): даже с правильным словарём AND-семантика остаётся, и русский вопрос с двумя-тремя словами, которых нет в нужном чанке, не получит keyword-подтверждения.
- Последствие для `matchType`: метка «keyword + semantic» (`both`) почти не встречается на длинных запросах, а значит, пассажи без подтверждения отсекаются порогом расстояния и могут пропасть из выдачи.

## Предложение
- Строить запрос в два шага: сначала строгий (`websearch_to_tsquery`, как сейчас). Если он вернул меньше `KEYWORD_MIN_HITS` (по умолчанию 3) строк, выполнить ослабленный запрос: термы, соединённые через `|` (OR), ранжирование `ts_rank_cd` (чанки с большим числом совпавших термов получают больший ранг, это естественно работает с RRF).
- Ослабленный `tsquery` собирать в SQL без интерполяции пользовательского текста: `to_tsquery('english', array_to_string(tsvector_to_array(to_tsvector('english', $1)), ' | '))`. `tsvector_to_array` доступна с PG 13 (в compose используется PG 16); стоп-слова отбрасываются самим словарём.
- Для безопасности производительности ограничить число термов (например, 12 первых по длине) и оставить `LIMIT CANDIDATES_PER_METHOD`.
- Включать ослабление флагом `KEYWORD_RELAXED=true` (по умолчанию `true` после проверки на eval-наборе из `IMPROVEMENTS.md` п. 2; до его появления — `false`, чтобы поведение по умолчанию не менялось).
- В `matchType` ничего не менять: ослабленное совпадение остаётся `keyword`.

## Критерии приёмки
- Юнит-тест построения запроса (чистая функция, SQL не нужен): стоп-слова отброшены, лимит термов соблюдается, пустой результат не ведёт к ошибке синтаксиса `tsquery` (запрос из одних стоп-слов → ослабление пропускается).
- Интеграционный/ручной сценарий: документ с текстом «Administrator password reset procedure» и запрос «how can I reset the administrator password quickly» — без флага чанк приходит только из вектора, с флагом `matchType = both`.
- На eval-наборе (когда он появится) recall@5 и MRR с флагом не хуже, чем без него; цифры записать в PR.
- Время ключевой ветки на корпусе из 10k чанков не растёт более чем на 20 % (замер `EXPLAIN ANALYZE` приложить).

## Контракт
`/api/search` не меняется. Новая env-переменная `KEYWORD_RELAXED` (и опционально `KEYWORD_MIN_HITS`) добавляется в `.env.example` и README.
