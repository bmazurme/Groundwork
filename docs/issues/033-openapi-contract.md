# Issue 033: OpenAPI-описание API и проверка совместимости контракта

**Метки:** backend, frontend, api, docs

## Проблема
Контракт `/api` существует только в коде: типы фронтенда (`apps/frontend/src/api/types.ts`) копируют серверные вручную (Issue 004 предлагает общие типы, но не описание для внешних клиентов). Правило проекта «не меняй публичный контракт без необходимости» нечем проверить: случайное переименование поля (`failureReason`, `matchType`) заметно только во время выполнения. Планируемые SSE-стриминг, обратная связь и пагинация (Issue 032) увеличат поверхность API. Интеграторам (скрипты загрузки, eval-харнесс) нужна машинно-читаемая спецификация.

## Предложение
1. `@nestjs/swagger` (новая зависимость: генерирует OpenAPI 3 из декораторов и DTO; обоснование и `npm audit` — в PR). Ui на `/api/docs` включается только вне production или флагом `API_DOCS_ENABLED`.
2. Описать DTO ответов классами с `@ApiProperty` (или плагином CLI Nest, чтобы не дублировать типы), загрузку файла как `multipart/form-data`, коды ошибок.
3. Скрипт `npm run openapi:generate -w backend` пишет `apps/backend/openapi.json` без запуска БД (приложение создаётся с заглушками провайдеров) и коммитится в репозиторий.
4. CI-шаг: перегенерировать и сделать `git diff --exit-code`; для изменений, ломающих совместимость, использовать `oasdiff`/`openapi-diff` в режиме «только предупреждение» на первом этапе.
5. Опционально: генерация типов фронтенда из `openapi.json` (`openapi-typescript`, dev-зависимость) и удаление ручных копий — решать отдельным PR.

## Критерии приёмки
- `/api/docs` показывает все текущие эндпоинты (`/documents`, `/documents/:id/chunks`, `DELETE`, `/search`, `/health`) со схемами, совпадающими с реальными ответами (сверка тестом: ответ интеграционного теста валидируется по схеме).
- Изменение имени поля в DTO без обновления `openapi.json` валит CI.
- Поведение API не меняется.
