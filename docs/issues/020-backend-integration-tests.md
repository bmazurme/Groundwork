# Issue 020: Нет интеграционных тестов бэкенда: e2e-заготовка не запускается в CI, а Nest-шаблонный тест не отражает реальные маршруты

**Метки:** testing, ci, backend

## Проблема
Найдено чтением `apps/backend/test/app.e2e-spec.ts`, `main.ts`, `.github/workflows/ci.yml`, `embeddings.module.ts`.
- `test/app.e2e-spec.ts` — шаблон Nest: обращается к `/health`, тогда как в приложении глобальный префикс `api` задаётся только в `main.ts` (`app.setGlobalPrefix('api')`), а в тесте он не подключён. Тест проверяет не то приложение, которое запускается, а скрипт `test:e2e` в CI не вызывается.
- CI запускает `npm run test -w backend -- --passWithNoTests`, поэтому «зелёные» тесты сейчас — это ноль тестов (`IMPROVEMENTS.md` п. 2 предлагает юнит-тесты и eval, но не интеграционный слой).
- `AppModule` через `EmbeddingsModule` при старте загружает ONNX-модель (`warmUp`), то есть любой тест, поднимающий модуль, зависит от скачивания сотен МБ. Подменить провайдер в тесте можно (`overrideProvider(EMBEDDINGS_PROVIDER)`), но фабрика провайдера асинхронная и инициализируется до подмены, пока не отделён выбор реализации.
- Требование задания — хотя бы один сценарий «загрузка → `indexed` → поиск → ответ с цитатами» — без такой инфраструктуры не выполнить повторяемо. Cypress-сценарий в `e2e`-job поднимает весь стек Docker и медленный.
- Настройка приложения (префикс, CORS, будущие `ValidationPipe`/`helmet` из Issue 002) дублируется между `main.ts` и тестами.

## Предложение
1. Вынести настройку приложения в `configureApp(app)` (префикс, CORS, pipes) и использовать её и в `main.ts`, и в тестах. Рефакторинг минимален и нужен именно для тестируемости.
2. `FakeEmbeddingsProvider` (детерминированный хеш-эмбеддинг нужной размерности `EMBEDDING_DIMENSIONS`, без модели) и переопределение провайдера в тестах. Чтобы подмена работала до `warmUp`, выбор провайдера вынести в отдельную фабрику, которую тест подменяет целиком. Реальный ONNX остаётся только в Cypress/eval.
3. Интеграционный набор `test/*.int-spec.ts` на реальных Postgres (pgvector), Redis и MinIO из service containers GitHub Actions (локально — `docker compose up -d postgres redis minio`): загрузка Markdown → ожидание `indexed` (опрос с таймаутом) → `GET /api/search` возвращает ожидаемый документ → `DELETE` удаляет чанки (каскад). Отдельная БД на прогон (`CREATE DATABASE` или схема), чистка в `afterAll`.
4. Скрипт `npm run test:int -w backend`; в CI отдельный шаг, `--passWithNoTests` убрать (после того как появятся юнит-тесты из `IMPROVEMENTS.md` п. 2).
5. Исправить/заменить шаблонный `app.e2e-spec.ts`.

Новых зависимостей не требуется (`supertest`, `jest` уже есть). Testcontainers не нужен: в CI service containers проще и быстрее.

## Критерии приёмки
- `npm run test:int -w backend` на чистой машине с поднятыми сервисами проходит без загрузки модели и без доступа в интернет.
- Тест сценария «загрузка → indexed → поиск» падает, если сломать вставку чанков или JOIN в поиске (проверить мутацией вручную и записать в PR).
- Тест на повторную загрузку: версия растёт, чанки не дублируются.
- Время набора — до 1 минуты на CI.

## Риски
Хеш-эмбеддинг не передаёт семантику, поэтому тесты проверяют конвейер и контракт, а качество поиска остаётся за eval-набором на реальной модели. Это нужно явно написать в README.
