# Issue 031: Задержка поиска: эмбеддинг запроса блокирует event loop, нет кеша и таймаутов

**Метки:** performance, backend, search

## Проблема
Найдено чтением кода (`search.service.ts`, `local-onnx-embeddings.provider.ts`, `documents.processor.ts`); замеров нет.
- `LocalOnnxEmbeddingsProvider.embed()` исполняется в основном процессе Node вместе с HTTP-сервером и BullMQ-воркером. Пока воркер эмбеддит чанки документа, запросы `/api/search` и `/api/health` ждут своей очереди в event loop. Во время индексации крупного файла поиск и health-check могут задерживаться, а health-check в Docker/Swarm способен пометить контейнер как нездоровый.
- Эмбеддинг запроса считается заново на каждый вызов. Повторные запросы (пользователь обновил страницу, фронтенд ретраит, будущий eval-прогон по одним и тем же вопросам) платят полную цену.
- У двух SQL-запросов поиска нет `statement_timeout`; при росте корпуса долгий запрос займёт соединение пула (связано с Issue 024).
- Длина `q` не ограничена: длинная строка уходит в токенайзер модели и в `websearch_to_tsquery` (пересекается с Issue 002, но там нет ограничения именно для пути эмбеддинга).

## Предложение
1. **Кеш эмбеддингов запросов.** Небольшой LRU в памяти (`Map` с вытеснением, ~500 записей, ключ — нормализованный текст запроса + идентификатор модели из Issue 014). Размер из env `QUERY_EMBEDDING_CACHE_SIZE` (0 = выключен). Новых зависимостей не требуется.
2. **Вынос ONNX из event loop.** Вариант A: `worker_threads` внутри `LocalOnnxEmbeddingsProvider` (интерфейс `EmbeddingsProvider` не меняется). Вариант B: отдельный процесс-воркер индексации (согласуется с ролью воркера из Issue 011). Начать с замера: p95 `/api/health` и `/api/search` во время индексации файла на ~2 МБ; делать вариант A, только если задержка подтверждена.
3. **Таймауты.** `SET LOCAL statement_timeout` (env `SEARCH_STATEMENT_TIMEOUT_MS`, по умолчанию 5000) для обоих запросов поиска; понятная ошибка 503 вместо зависания.
4. **Лимит длины запроса** `MAX_QUERY_LENGTH` (по умолчанию 500 символов) с ответом 400; фронтенд показывает счётчик/ограничение через `maxLength`.

## Критерии приёмки
- Юнит-тест кеша: повторный запрос не вызывает `embed()`; вытеснение по LRU; размер 0 отключает кеш.
- Нагрузочная проверка (скрипт в `docs` или `scripts/`): p95 `/api/health` во время индексации не превышает заданный порог; результаты приложены к PR.
- Тест на 400 при слишком длинном `q` и на 503 при срабатывании таймаута.
- Поведение поиска и контракт `/api/search` не меняются. Новые env добавлены в `.env.example` и README.
