# Issue 030: Резервное копирование и восстановление (Postgres + S3)

**Метки:** ops, docs, reliability

## Проблема
Состояние системы распределено между Postgres (`documents`, `document_chunks`) и S3/MinIO (оригиналы). В README и `docker-compose.yml` нет ни слова о бэкапе и восстановлении:
- Данные Postgres лежат в именованном томе `postgres-data`, MinIO — в своём томе. CI выполняет `docker compose down -v`; на машине разработчика та же команда необратимо стирает обе части. Предупреждения в README нет.
- Двух хранилищ достаточно, чтобы после частичного восстановления (например, только БД из дампа) получить документы, у которых нет объекта в S3: повторная индексация (Issue 016) тогда упадёт на `download`, а пользователь увидит только `failed`.
- Эмбеддинги можно вычислить заново из чанков, но только если сохранён текст и известна модель (Issue 014); дамп таблицы с `vector(384)` без записи о модели нельзя безопасно использовать при смене провайдера.
- Миграции (`IMPROVEMENTS.md`, п. 4) добавят таблицу версий схемы, и восстановление дампа из другой версии схемы без проверки сломает приложение.

## Предложение
1. Раздел README «Backup & restore»: что именно хранится где, что нужно копировать (дамп Postgres и бакет S3), что можно пересоздать (Redis, индексы HNSW/GIN, эмбеддинги) и что при этом теряется.
2. Скрипты `scripts/backup.sh` и `scripts/restore.sh` (без новых зависимостей): `docker compose exec -T postgres pg_dump -Fc` и `mc mirror`/`aws s3 sync` для бакета в каталог с отметкой времени и файлом `manifest.json` (версия схемы, `EMBEDDINGS_PROVIDER`, имя модели и размерность, число документов, контрольные суммы дампа). Скрипты проверяют, что манифест совпадает с текущей конфигурацией, и отказываются восстанавливать при несовпадении размерности/модели без явного флага `--force`.
3. Команда проверки целостности `npm run verify:storage -w backend`: все `documents.s3_key` существуют в бакете, и наоборот (общая часть с Issue 013).
4. Проверка восстановления в CI по расписанию (`workflow_dispatch`/`schedule`, отдельный файл, не на каждый PR): поднять стек, загрузить фикстуру, сделать бэкап, `down -v`, восстановить и убедиться, что поиск возвращает тот же результат. Бэкап, который ни разу не восстанавливали, бэкапом считать нельзя.
5. Предупреждение о `down -v` в README и в комментарии к `volumes:` в compose-файле.

## Критерии приёмки
- Выполненный и описанный в PR цикл: загрузка документа → бэкап → `docker compose down -v` → восстановление → тот же документ в списке со статусом `indexed` и тот же результат поиска.
- Восстановление с манифестом другой размерности отклоняется с понятным сообщением.
- Скрипты проходят `shellcheck` (CI-шаг без новых зависимостей приложения).
- Контракт `/api` не меняется.
