# Issue 011: Пропускная способность индексации: эмбеддинги по одному и общий процесс с API

**Метки:** performance, reliability

## Проблема
Найдено чтением `documents.processor.ts`, `embeddings.interface.ts`, `local-onnx-embeddings.provider.ts`, `queue.module.ts`:
- Процессор вызывает `embeddings.embed(chunk)` и затем `INSERT` для каждого чанка последовательно. Для документа в сотни чанков это сотни отдельных вызовов модели и запросов к БД. Интерфейс `EmbeddingsProvider` не имеет пакетного метода.
- Воркер BullMQ и HTTP-API живут в одном процессе, а ONNX-инференс идёт в том же процессе. Пока индексируется большой документ, запросы поиска (которым тоже нужен `embed`) стоят в очереди за ним, и задержка поиска растёт.
- Конкурентность воркера не задана явно (по умолчанию 1), значит, один тяжёлый PDF блокирует все остальные загрузки.
- Время индексации и размер документа нигде не фиксируются, оценить эффект оптимизаций нечем.

## Предложение
- Добавить в `EmbeddingsProvider` необязательный `embedBatch(texts: string[]): Promise<number[][]>`; для ONNX — батчи по `EMBED_BATCH_SIZE` (по умолчанию 16), для Ollama — эндпоинт `/api/embed` с массивом. Если метода нет, процессор откатывается на цикл по `embed`. Контракт и размерность не меняются.
- Вставка чанков одним многострочным `INSERT` на батч (согласуется с транзакцией из п. 3 `IMPROVEMENTS.md`).
- Режим `APP_ROLE=api|worker|all` (по умолчанию `all`, поведение прежнее): воркер можно запустить отдельным процессом/контейнером из того же образа. Конкурентность — `INDEX_CONCURRENCY`.
- Логировать длительность этапов (download / parse / chunk / embed / insert) и сохранять `indexed_ms` в `documents` (необязательное поле API, после миграций).

## Критерии приёмки
- Юнит-тест: процессор с `embedBatch` и без него даёт одинаковые чанки и векторы (на фейковом провайдере).
- Замер до/после на документе от 200 чанков: время индексации и p95 задержки `/api/search` во время индексации. Числа записать в PR.
- Значения env по умолчанию сохраняют текущее поведение.

## Риски
Батч-эмбеддинг может чуть менять числа из-за паддинга: сверить косинус с поштучным результатом (допуск ~1e-5). Память растёт с размером батча.
