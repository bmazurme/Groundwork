# Issue 016: Нет ручной повторной индексации документа и диагностики `failed` в интерфейсе

**Метки:** ux, backend, frontend, reliability

## Проблема
- Единственный способ переиндексировать документ — заново загрузить файл с тем же именем (`documents.service.ts`, `upload`): это увеличивает `version`, создаёт новый объект в S3 и стирает прежний. Если документ ушёл в `failed` из-за временного сбоя (S3, эмбеддер, Redis), а файл не менялся, пользователь вынужден искать оригинал и грузить его снова.
- После смены парсера или чанкера (Issue 001, 006, 007) владельцу нужен способ пересчитать индекс уже загруженных документов. Issue 014 предлагает CLI `reindex --stale`, но у пользователя в интерфейсе такого действия нет.
- Причина `failed` (`failure_reason`) в API есть, а в `DocumentsTable.tsx` показана только как `title` у метки статуса: на тач-устройствах её не видно, длинный текст не читается, скопировать его неудобно.
- `queue.add('process', ...)` не задаёт `jobId`. Два быстрых клика по «повторить» поставили бы два параллельных задания на один документ, и оба делают `DELETE` + `INSERT` чанков.

## Предложение
Бэкенд:
- `POST /api/documents/:id/reindex` (202 + текущая запись `DocumentRecord`). Допустим для статусов `indexed` и `failed`; для `pending`/`indexing` ответ 409 «уже в очереди». `:id` через `ParseUUIDPipe` (404, если документа нет).
- Метод ставит документ в `pending`, очищает `failure_reason`, **не** меняет `version` и **не** трогает объект в S3. Чанки не удаляются заранее: старые остаются до момента, когда процессор заменит их (согласовано с транзакцией из `IMPROVEMENTS.md`, п. 3), поэтому поиск не теряет документ на время переиндексации.
- Идемпотентность: ``queue.add('process', { documentId }, { jobId: `reindex-${id}-${version}-${updatedAtMs}` })`` либо проверка статуса в одном `UPDATE ... WHERE status IN ('indexed','failed') RETURNING`, чтобы второй конкурентный вызов получил 409, а не второе задание.
- Необязательно: `POST /api/documents/reindex?status=failed` для массового запуска (лимит на число документов за вызов через env).

Фронтенд:
- В `DocumentsTable` кнопка «Переиндексировать» (иконка Gravity UI) в колонке действий для `failed`/`indexed`; `useMutation` + инвалидация `['documents']` (опрос раз в 2 с уже включается автоматически, пока есть активные статусы).
- Для `failed` показывать причину в раскрываемой строке или `Popover` рядом с меткой, с кнопкой «Скопировать».
- Подтверждение не нужно (действие безопасно и обратимо), но на время запроса кнопка в `loading`.

## Критерии приёмки
- Юнит-тесты сервиса: `failed` → 202 и новая задача; `indexing` → 409; несуществующий id → 404; два конкурентных вызова создают ровно одну задачу.
- Интеграционный сценарий (см. Issue 020): документ → `failed` (подмена эмбеддера на бросающий исключение) → исправление → `reindex` → `indexed`, число чанков не удвоилось.
- Ручная проверка: во время переиндексации старый документ остаётся находимым в поиске.

## Контракт
Добавляется один маршрут; существующие не меняются. `DocumentRecord` не меняется. Фронтенд обновляется в том же коммите.
