# Предложения по улучшению Groundwork

Анализ по коду `apps/backend` и `apps/frontend` (снимок `main`). Это только предложения: код не менялся, приложение и тесты не запускались (анализ статический). Пять пунктов в порядке приоритета.

## 1. Полнотекстовый поиск не работает для русского языка

**Проблема.** В `search/search.service.ts` и в GIN-индексе (`database/schema.ts`) жёстко зашит словарь `'english'`: `to_tsvector('english', content)`. Для русских запросов и русских документов keyword-ветка почти ничего не находит (нет стемминга, русские стоп-слова не отбрасываются). Гибридный поиск для русского фактически превращается в чисто векторный. При этом продукт заявлен как RU+EN, а эмбеддер выбран мультиязычным именно ради этого.

**Предложение.**
- Добавить в `document_chunks` колонку `fts tsvector`, сгенерированную из `to_tsvector('russian', content) || to_tsvector('english', content)`, и GIN-индекс по ней. Запрос строить через `websearch_to_tsquery` для обоих словарей, соединённых через `||`.
- Это изменение схемы, поэтому делать его лучше после пункта 4 (миграции).
- Порог `SEMANTIC_ONLY_MAX_DISTANCE = 0.72` подобран по одному запросу на маленьком корпусе (так сказано в комментарии). Вынести его в env и проверить на eval-наборе (пункт 2).

**Эффект.** Заметно растёт качество поиска на русском; риск небольшой.

## 2. Нет тестов и нет измерения качества поиска

**Проблема.** В `apps/backend` нет ни одного `*.spec.ts`, а CI запускает тесты с `--passWithNoTests`, поэтому зелёный CI ничего не гарантирует. Чистая логика (`chunkText`, `reciprocalRankFusion`, `formatFromFilename`) легко тестируется, но не покрыта. Качество поиска нигде не измеряется, а README заявляет «with the evals to prove it».

**Предложение.**
- Вынести `reciprocalRankFusion` в отдельный файл и покрыть юнит-тестами вместе с `chunkText` (code fence, mermaid, frontmatter не режутся; границы абзацев и предложений) и парсингом.
- Убрать `--passWithNoTests` из CI.
- Добавить небольшой golden-набор RU/EN вопросов с ожидаемыми документами и скрипт `npm run eval` (recall@k, MRR, hit-rate, JSON + таблица), затем запускать его в CI на PR с порогом регрессии.

**Эффект.** Появляется защита от регрессий и объективная база для изменений в пунктах 1 и 5.

## 3. Надёжность загрузки и индексации

**Проблемы** (все в `documents.service.ts` и `documents.processor.ts`):
- Нет лимита размера и проверки содержимого. `memoryStorage()` держит весь файл в памяти, формат определяется только по расширению.
- Повторная загрузка файла с тем же именем делает `SELECT` и затем `INSERT` или `UPDATE` без уникального ограничения на `name`. Два параллельных запроса создадут дубликаты.
- Процессор делает `DELETE` чанков и затем вставляет их по одному, последовательно, вне транзакции. Если процесс упадёт посередине, документ останется без части чанков. Задача добавляется без `attempts` и `backoff`, поэтому временный сбой S3 или эмбеддера сразу даёт `failed`.
- Во время переиндексации поиск может возвращать частично записанные чанки. Фильтра по `status = 'indexed'` в запросах поиска нет.
- `:id` не проверяется как UUID, поэтому `GET /documents/abc/chunks` приводит к ошибке Postgres и ответу 500 вместо 400/404.

**Предложение.**
- Лимит `MAX_UPLOAD_BYTES` через multer `limits`.
- Уникальный индекс на `name` и `INSERT ... ON CONFLICT`.
- Транзакция: удаление и вставка чанков одним батчем (`unnest` или многострочный `INSERT`), эмбеддинги считать до открытия транзакции.
- `attempts: 3` с экспоненциальным `backoff` в `queue.add`.
- `JOIN documents ... WHERE d.status = 'indexed'` в поиске.
- `ParseUUIDPipe` на параметры `:id`.

**Эффект.** Нет потери данных при сбоях и нет 500 на мусорных запросах.

## 4. Версионируемые миграции вместо `ensureSchema`

**Проблема.** `database/schema.ts` — набор `CREATE ... IF NOT EXISTS`. Любое изменение существующей таблицы (колонка из пункта 1, уникальный индекс из пункта 3, таблицы `feedback` и `query_log`) в таком виде применить нельзя. Размерность вектора берётся из константы, и без явной истории схемы её смена будет молча сломана.

**Предложение.** `node-pg-migrate` (лёгкий, работает поверх `pg`). Миграция `0001` — текущая схема, написанная идемпотентно, чтобы на уже существующей базе она ничего не ломала и не теряла данные. Запуск миграций отдельным шагом (`npm run migrate`) перед стартом приложения и в Docker/CI. Одна новая зависимость, перед добавлением проверить `npm audit`.

**Эффект.** Это блокер для почти всех дальнейших изменений схемы, поэтому делать его стоит раньше пунктов 1 и 3.

## 5. Реранкер и LLM-синтез ответа вместо заглушки

**Проблема.** Поле `answer` — это фиксированная строка «retrieval only — LLM answer synthesis is not wired up yet». Это главный пробел относительно цели продукта. Кроме того, RRF учитывает только ранги и не оценивает релевантность пары «запрос — фрагмент», поэтому порядок топ-5 шумный.

**Предложение.** Следовать уже принятому в проекте подходу «провайдер за интерфейсом, выбор через env» (как `EmbeddingsProvider`):
- `Reranker` (`RERANKER_PROVIDER=none|onnx`, по умолчанию `none`, мультиязычная cross-encoder модель) поверх кандидатов после RRF.
- `LlmProvider` (Ollama и OpenAI-совместимый клиент): ответ строится только по найденным фрагментам, с цитатами `[документ/чанк]`, а при нехватке контекста возвращается «в документах ответа нет». Стриминг через SSE и отображение потока в `SearchPanel`.
- Контракт `/api/search` сохранить обратно совместимым: добавить поля (`citations`) и отдельный эндпоинт для стрима, а не менять существующие.

**Эффект.** Закрывает основное расхождение между README и реальным поведением. Выигрыш реранкера нужно подтвердить на eval-наборе из пункта 2.

**Рекомендуемый порядок:** 4 → 2 → 1 → 3 → 5. Миграции дают основу для изменений схемы, eval позволяет измерять эффект остальных пунктов.
